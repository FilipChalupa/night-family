Protocol changelog Night Family WebSocket protocol — Household ⇄ Member

What changed in each PROTOCOL_VERSION. Newest first. The current value lives in shared/src/protocol.ts; versioning rules are in README · Protocol versioning and the discipline for picking a level is in AGENTS · Protocol changes.

3.4.0

Members can connect to MCP (Model Context Protocol) servers — Slack, Linear, Jira, Drive, … — and expose their tools to the agent. The handshake now reports which servers a Member actually connected to, so the dashboard can show what each Member can reach.

  • Added optional mcp_servers to handshake (Member → Household): an array of { name, tool_count } for each connected server (tool count is post-allowlist). Omitted when no MCP is configured; lists servers that connected, not merely what's configured. Surfaced on the Member detail page. Old Members simply omit it.

3.1.0

Refresh-on-demand for the Member's accessible-repos allowlist — Household can now ask a Member to re-fetch /user/repos mid-session, and Members report failures back. Lets newly-granted collaborator access land without a Member restart.

  • Added repos.refresh (Household → Member). Carries an opaque reason string for diagnostics (conventional values: schedule_edge, queue_mismatch, manual, periodic). Household pushes this on three triggers: day↔night schedule edges, queued tasks whose repo isn't in any member's allowlist, and the POST /api/members/:id/refresh-repos admin endpoint.
  • Added member.repos (Member → Household). Replaces the handshake-time repos cache with the just-fetched list; Household persists and re-dispatches against queued tasks immediately.
  • Added member.repos_error (Member → Household). Reports a refresh failure (PAT revoked, GitHub rate limit, etc.) so the previous list is kept and the operator can see why. Carries the original reason and the error message.
  • Members run a slow safety-net refresh every 6 hours so a fleet with no schedule edges and no incoming tasks still picks up permission changes eventually.

3.0.0

Schedule evaluation moves to Household; estimate removed; rebase dotažen jako TaskKind; pár dead-letter zpráv pryč. Skills are now static per session.

  • handshake.schedule (required) — Members ship their full Schedule (timezone + nightWindows[]) on connect. Household evaluates the schedule per-session and gates dispatch accordingly. Members no longer run a local ScheduleController.
  • Removed member.skills_updated (Member → Household). Skills are now configured statically on the Member (env SKILLS) and announced once at handshake; they don't change during a session.
  • Removed schedule.override (Household → Member). Admin-driven overrides are now Household-internal state evaluated alongside the schedule; the Member doesn't need to know.
  • Removed estimate from Skill and TaskKind; removed estimating from TaskStatus. Triage's plan output already carries the size estimate, so the standalone estimate step is gone for good.
  • Added rebase to TaskKind (not a new Skill). When a PR's base branch moves and the head goes behind_by > 0, Household enqueues a regular rebase task pointing at the parent implement task; the dispatcher routes it to a Member with the implement skill (prefer the original implementer for cache warmth). The Member's runner handles kind === 'rebase' with a deterministic git-only path (no LLM): fetch base, git rebase, push --force-with-lease; conflicts fail fast for now.
  • Removed task.rebase_suggested (Household → Member). The rebase TaskKind above replaces it; rebase is now first-class work tracked in the tasks table.
  • Removed never-set optional fields from heartbeat-path messages: MsgMemberBusy.task_title and MsgHeartbeat.current_task_title. Members never populated them; consumers always derived the title from the task store anyway.

2.2.0

Triage workflow + deterministic comment attribution.

  • Adds triage task kind and skill. Household creates triage tasks on issue.opened and human issue_comment.created. Triage agent reads the issue thread, decides whether to ask a clarifying question or to write a plan comment; in the plan case, an implement task is enqueued for that issue. Day members offer triage; night members offer triage + implement.
  • Deprecates estimate as a task kind and skill (still in the type union for forward compat, but Household no longer creates these tasks; estimation is folded into the triage plan).
  • Comment attribution: every PR body, PR comment, PR review and issue comment posted by a Member ends with a deterministic block: 
    ---
🤖 Authored by Night Family member [`<login>`](…) · task [`<id>`](…)
<!-- night-family:member=<id> task=<id> -->
    Household uses the HTML comment to detect bot-authored content and skip its own webhooks (so we don't trigger triage cycles on our own comments). Server-side for PRs (workspace.ts) and via dedicated agent tools (post_issue_comment / post_pr_comment / post_pr_review) for everything else; the bash tool refuses gh issue/pr comment/review/create/edit with a redirect.

2.1.0

Schedule-driven skill changes and admin overrides. Additive only — old peers ignore both new message types.

  • member.skills_updated (Member → Household): announces the Member's effective skill set has changed (e.g. local night/day transition fired, override expired). Household replaces the cached skills for that session; the dispatcher reads fresh skills on the next match attempt.
  • schedule.override (Household → Member): admin-driven temporary override of the schedule, with expires_at (ISO). skills: null clears the active override.

2.0.0

Per-member GitHub identity. The single Household-side PAT (sent to Members via task.assigned.github_token) is replaced by per-Member PATs in Member env. Wire impact:

  • task.assigned no longer carries github_token or repo_url. Members read their own PAT from env (GITHUB_PAT) and derive the repo URL from task.repo.
  • handshake adds a required display_name (pretty name from GitHub /user). member_name is now constrained to be the GitHub login.

Old Households reject new Members because the handshake schema differs; old Members reject new Households for the same reason. There's no graceful fallback — operators must update both sides together.

1.1.0

Added firstConnectedAt to the MemberSnapshot payload pushed over /ws/ui (earliest known connection for a member_id, scanned across all token usage logs). Old UI clients ignore the field; old Households simply omit it. Member↔Household wire messages unchanged.

1.0.0

Initial semver-tracked release. Switched protocol_version from a single integer to a "major.minor.patch" string, added compatibility checks (compareProtocolVersions), and started warning on minor skew instead of rejecting outright. Household now also reports its own protocol_version back to Member in handshake.ack. Both sides validate every incoming WebSocket message against a runtime schema (parseMemberToHousehold / parseHouseholdToMember); messages that fail validation are dropped with a log entry, which is the runtime implementation of the "ignore unknown messages" half of the minor-bump compatibility rule.

Add an entry whenever PROTOCOL_VERSION is bumped. Edit on GitHub.
