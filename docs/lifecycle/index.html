Task lifecycle From labeled issue to merged PR — every state, every transition

A Night Family task is a row in Household's database with a finite-state status. This page walks through every state, what triggers each transition, and the corner cases (retries, disconnects, self-review).

Task kinds

What the dispatched agent is asked to do. Each kind maps to a Member skill.

  • triage — read a fresh issue and either ask a clarifying question or write a plan comment. Day-mode Members offer this skill on its own.
  • implement — branch, edit, commit, push, open a draft PR. Night-mode Members offer this in addition to triage.
  • review — read a PR diff and post a review with verdict approved, changes_requested, or commented. Tracked as a child review job, not a top-level task.
  • respond — reply to a PR comment thread (manually queued).
  • summarize — produce a textual summary of recent activity (manually queued).
  • estimate — deprecated as of protocol 2.2.0. Folded into the triage plan output.

Statuses

The full set of values tasks.status can take.

new Awaiting an estimate dispatch (legacy; new code uses queued directly).
estimating An estimate task is in flight on a Member.
queued Ready to dispatch. The dispatcher will claim it for a matching idle Member.
assigned Sent to a Member; waiting for the 30-second ack.
in-progress Member acked and is actively working.
in-review Draft PR is open; review jobs dispatched to other Members and humans.
awaiting-merge An approving review came in on a clean PR. Waiting on a human to merge.
done Terminal — PR merged (or non-PR task completed).
failed Terminal — agent error after retries, PR closed without merge, or quota exceeded.
disconnected Reserved for Member states (not used on tasks today).

The happy path

The day-to-day flow is driven by GitHub webhooks, with the dashboard's manual task-entry form as a fallback. Walking through one issue end-to-end:

  1. Issue arrives. Someone opens or labels a GitHub issue with night. Household's webhook handler creates a triage task (queued) for it.
  2. Triage dispatch. The dispatcher claims the task for an idle Member with the triage skill — repo allowlist permitting. Status: queued → assigned → in-progress.
  3. Triage decides. The triage agent reads the issue thread and emits one of two outcomes:
    • question: a clarifying comment is posted on the issue. The triage task ends in done; nothing else happens until the human replies (which spawns a fresh triage on issue_comment.created).
    • plan: a plan comment is posted, and Household auto-spawns a sibling implement task in queued for the same issue. The triage task moves to done.
  4. Implement dispatch. An idle Member with the implement skill claims the task. Member clones the repo (own PAT), checks out a branch named pr/night/<task-id-prefix>-<slug>.
  5. Agent loop runs. The agent edits, runs commands, commits as Night Family <noreply+night@local> with a Co-Authored-By: Night <member-name> trailer.
  6. PR opens. The Member pushes and runs gh pr create (draft). The PR body ends with a deterministic 🤖 Authored by Night Family member footer that doubles as a bot-detection marker for Household's webhook deduper. Household sees pull_request.opened, matches the PR to the task by branch prefix, and transitions in-progress → in-review.
  7. Parallel review. Household creates up to two review jobs and dispatches them to idle Members with the review skill, preferring reviewers whose GitHub login differs from the PR author. Each reviewer posts a verdict.
  8. Approval. When a review with approved comes in on a mergeable_state: clean PR, the task moves in-review → awaiting-merge. A push notification fires.
  9. Merge. A human merges. pull_request.closed with merged: true moves the task to done. A pr.merged notification fires. Members never self-merge — that's a branch-protection job.

Branching paths

Changes requested

When a reviewer submits state: changes_requested, the task goes in-review → queued (the failureReason is cleared). The assignedMemberId is intentionally preserved as a hint, and the dispatcher gives that Member first dibs through claimNextForPreferredMember:

Bias toward the original implementer. Reusing the same Member keeps its workspace clone and its LLM prompt cache warm — re-dispatching to a stranger forces a fresh clone and a cache miss. If the original Member is offline, busy on something else, or no longer offers implement, the task falls through to the generic queue and any matching idle Member can claim it.

A push notification "Review requested changes" fires on this transition. The re-implement attempt then follows the same path back through assigned → in-progress → in-review; review jobs are dispatched again, this time preferring reviewers different from the persisted pr_author_login (the original author, not the current assignee).

Self-review fallback

A solo-PAT setup can't easily satisfy GitHub's "1 approving review" rule because a Member can't approve its own PR. Household handles this two ways:

  • If no different-login reviewer is connected at all, same-login self-review is dispatched immediately.
  • If a different-login reviewer is connected but currently busy, the review job is queued pending. After 10 minutes a wakeup timer fires and a same-login Member can claim it as a fallback.

Cancellation

Removing the night label or closing the issue cancels the matching task — unless it's already in done or awaiting-merge (those terminal-ish states are owned by the PR webhook). An in-flight Member receives a task.cancel message.

PR closed without merge

pull_request.closed with merged: false moves the task to failed with reason pr_closed_without_merge. If a Member is still busy on the task, it's sent task.cancel.

Stale base detected

When the PR webhook reports behind_by > 0 and a Member is still assigned, Household sends task.rebase_suggested to that Member. The Member chooses whether to rebase and push.

Failure handling

Auto-retry on implement

If a Member reports an implement task as failed, the dispatcher auto-retries up to 3 times with exponential backoff: 1 min, 5 min, 15 min. The task returns to queued with nextRetryAt set; the assignedMemberId is preserved (same warm-cache benefit as changes_requested). After three failures the task is marked failed and a task.failed notification fires.

Quota exceeded

If the Member's LLM provider returns a quota error, the task fails with reason quota_exceeded and a quota_exceeded notification fires instead of the generic task.failed.

Ack timeout

After dispatching, Household waits up to 30 seconds for the Member's task.ack. No ack → the task returns to its previous queue status (queued or new) and is rotated to another Member on the next dispatch.

Member disconnect

When a Member's WebSocket drops, every task or review job it owned (statuses estimating, assigned, in-progress) is returned to its queue: tasks back to queued/new, review jobs back to pending. A member.disconnected notification fires. If the Member reconnects under a new sessionId quickly enough and resumes the same task IDs in its handshake, those are re-linked to the new session with status preserved.

Where the code lives

  • shared/src/protocol.ts — TaskKind, TaskStatus, the wire types.
  • household/src/tasks/dispatcher.ts — skill matching, retry logic, review-job creation, preferred-member bias.
  • household/src/tasks/store.ts — atomic status transitions, the claim methods.
  • household/src/github/handlers/pulls.ts — PR and review webhook handlers (changes_requested, approved, merged, closed).
  • household/src/github/handlers/issues.ts — issue label / open / comment handlers (triage spawning).
  • household/src/push/taskTransitions.ts — which transitions trigger a Web Push notification.
